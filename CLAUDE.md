# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

`AGENTS.md` (imported above) holds the conventions, security rules, env vars, and API list. This file adds what it leaves out, and notes where the code has moved past it.

## Commands

Neither package has a test runner or linter. Verification means running the type-check/build:

- `cd backend && npm run build` (`tsc`)
- `cd frontend && npm run build` (`tsc && vite build`)

Other scripts that `AGENTS.md` doesn't list:

- `cd backend && npm run start:deploy`: `prisma migrate deploy`, then start. For production, never use `migrate reset` there.
- `cd backend && npm run test:s3` / `npm run test:api-upload`: manual smoke scripts in `backend/src/scripts/`.
- `setup.sh` / `setup.ps1`: create `backend/.env` and `frontend/.env` with random secrets, run `npm install`, and generate the Prisma client.
- On Windows, if `prisma generate` fails because a file is locked, stop the running dev servers first.

## Architecture beyond AGENTS.md

**Two storage providers.** `ConnectedAccount.provider` is `google_drive` or `s3`. An S3-compatible account is a `ConnectedAccount` plus an `S3StorageConfig` row (encrypted keys, bucket, optional endpoint, `prefix` defaulting to `9drive`, optional `quotaBytes`). Code that touches a stored file has to branch on provider:
- Streaming: `modules/files/stream-file.ts` (`streamProviderFile`) sends work to `stream-google-file.ts` or `s3/s3.service.ts`.
- Quota: `syncGoogleQuota` (google.service) vs `syncS3Quota` (s3.service). Both write to `StorageAccount`.
- Upload: `ensureGoogleAppFolder` + Drive resumable upload vs `buildS3ObjectKey` + `uploadS3Object` (`@aws-sdk/lib-storage`).

**Upload routing** (`modules/uploads/upload.routes.ts`, `selectUploadAccount` → `selectAccount`). An explicit `targetAccountId` from the upload dialog is required as given. A folder's bound account (`Folder.connectedAccountId`) is tried first but is only a preference; if it lacks space, normal routing applies and the Drive file goes to that account's `9drive` root (`driveParentFor`). Normal routing:
1. Re-sync quota for any account whose last sync is more than 5 minutes old.
2. Subtract bytes already reserved by earlier files in the same multipart request.
3. Apply the user's `UploadRoutingPolicy` mode: `most_available` (default), `round_robin` (cursor kept in the DB), or `priority` (`priorityAccountIds`).
4. If `availableBytes` is null, treat the account as unlimited. When quotas are unknown, S3 accounts are preferred.

`handleUpload` is shared with the external API, mounted as `POST /api/v1/uploads` (`modules/public-api`). That route is guarded by `requireApiKey('files:upload')` in `middleware/api-key.middleware.ts`, not by `requireAuth`. API keys are stored hashed and carry scopes.

**Virtual vs physical.** Folders live in MySQL (`Folder.parentId` tree). When a Google account is connected, each folder also gets a Drive mirror under `9drive` (`Folder.providerFolderId`, bound to `Folder.connectedAccountId`), and Drive uploads into that folder go into the mirror. S3 objects are stored flat under the prefix. Folders and files are soft-deleted (`deletedAt`/`status`), which is what the Trash and Archived pages rely on.

**Google Drive import** (`modules/google/drive-sync.ts`, `syncGoogleDrive`). Each connected Google account's whole My Drive (`'me' in owners`, not trashed; shortcuts and non-exportable Google types skipped) is imported. The `9drive` app folder is the app root and its subfolders are app folders (`Folder.source = 'app'`). Everything else appears under one folder per account (`source = 'drive_root'`, name `Drive · email`, `providerFolderId` = My Drive's id), with Drive's tree mirrored as `source = 'drive'` folders. A full import lists everything and stores the Drive changes-feed token; later runs are incremental (`changes.list` from `ConnectedAccount.driveChangesToken`), with a full import at least daily or when the token is rejected. Runs: `POST /files/sync-google` (202 `running` after 45 s, keeps going), in the background after connecting, and every 30 min (`startDriveSyncScheduler`); one run per account at a time. Sync never changes Drive, only MySQL. Rules, shared by full and incremental runs (`Reconciler`): rows edited in the app during a run (`updatedAt` >= its start) are not overwritten (conditional `updateMany`); a parent Drive can't represent (another account, no mirror) is kept; user deletes stay out until restored, while rows sync deleted because they left Drive (`deletedBySync`) come back when they reappear. `drive_root` folders can't be renamed or moved, or deleted while connected; disconnecting an account calls `removeImportedDrive` (DB rows only, files stay in Drive). `GET /files?folderId=root` lists only top-level files.

**Memory with a large Drive.** One account can hold hundreds of thousands of files and tens of thousands of folders, so no code path may load all of them. A full import lists Drive a page at a time and keeps only the set of Drive ids it saw (for the sweep), plus the folder tree. An incremental run handles the changes feed a page at a time and loads only the folder rows that page refers to (`Reconciler.prefetchFolders`). Removing an import, folder delete, the move cycle check and file/folder lists all work in bounded batches or with caps. The frontend never asks for every folder: folder pickers search (`FolderPicker`, `GET /folders?q=`) and breadcrumbs use `GET /folders/:id/path`. Each sync run logs `[drive-sync] done` with `heapUsedMB`/`rssMB`; use it to size the backend heap cap. Pass a heap cap as a `node --max-old-space-size=<MB>` argument in the service's start command, not through `NODE_OPTIONS`, which the self-update build would inherit. Integration test: `backend/tests/drive-sync.integration.test.mjs` (needs a scratch DB, see its header).

**Thumbnails.** `GET /files` adds `thumbnailPath` for files that can have one (`utils/thumbnail.ts` `mayHaveThumbnail`: Drive images, videos, PDFs, office and Google documents; S3 images up to 15 MB). It is a signed URL (`/files/thumbnail/:id?exp&sig`, HMAC with a key derived from `JWT_ACCESS_SECRET`) because `<img>` can't send the bearer token; the expiry is rounded to 6-hour windows so the URL, and the browser's cached image, stay the same for hours. The route (before `requireAuth`) streams Drive's `thumbnailLink` at 480 px fetched with the account's token, or the S3 object. The frontend (`FileThumbnail`) lazy-loads it over the type icon in the grid and the details panel.

**Moves vs Google sync.** `PATCH /files/:id` and `PATCH /files/batch` also move the Drive file (`moveGoogleFile`) when the target folder has a Drive mirror on the file's account, or to the `9drive` root when moving to root. Otherwise the move is app-side only. Folder rename/move also changes Drive first (`applyDriveChange`): skipped when the bound account is disconnected, otherwise a Drive failure fails the request (502); a folder with a Drive mirror can only move within its own account. The Drive parent for uploads and moves comes from `driveParentForFolder`. Sync treats the Drive parent as the source of truth for `folderId`, except when the file's current folder can't be represented on Drive (bound to another account, or no mirror); then it keeps the app-side `folderId`.

**Google OAuth config comes from the DB, not env.** `env.ts` doesn't read `GOOGLE_*`. Those vars are read only by the seed scripts, which write a global `ProviderConfig` row (`userId` null) with encrypted credentials. It can also be set in Settings via `POST /system/google-config`. In Docker, `seed:google-config:docker` skips seeding when the credentials are blank or placeholders.

**Other modules missing from AGENTS.md:** `api-keys`, `audit-logs` (`utils/audit.ts` `createAuditLog`, shown on ActivityLogPage), `system` (admin-only via `middleware/admin.middleware.ts`: self-update, `update-log`, `google-config`), and `s3`.

**Self-update** (`POST /system/update`). For bare-metal installs, the backend spawns `update.sh` from the repo root (falls back to plain `git pull` if it's missing). The script fetches, refuses a diverged checkout, and builds everything in a git worktree at `.update-staging`: dependencies (`npm ci --include=dev`, or a copy of the live `node_modules` when the lockfile hash in `node_modules/.9drive-lock-hash` matches), `prisma generate`, `tsc --noEmitOnError`, `vite build`. Only when both builds pass does it swap `node_modules` and `dist` in by rename, fast-forward the checkout, run `prisma migrate deploy`, write `.update-pending`, and kill its parent backend with `SIGUSR2` so the supervisor (systemd `Restart=on-failure`) starts the new build. A failed run leaves the live tree untouched. The new backend writes `=== System Update Completed` to `update.log` on startup (`utils/app-version.ts`), which is what Settings waits for. The build runs inside the backend's cgroup, and Node caps its heap at about half of the unit's `MemoryMax`, so builds must stay small: backend `tsc` ~270 MB, frontend `tsc`/`vite build` ~400 MB. The version shown in Settings comes from `backend/package.json` via `GET /health`.

**Desktop app** (`desktop/`, Tauri 2). It wraps the same React app, built with `vite --mode desktop` (`VITE_DESKTOP=1` from `frontend/.env.desktop`, no PWA, output `frontend/dist-desktop`). Frontend code checks `isDesktop` (`lib/runtime.ts`). Tauri calls live only in `lib/desktop.ts`; web builds alias it to the stub `lib/desktop-web.ts` (`vite.config.ts`) so no Tauri code ships to browsers. The API base is the server address chosen at first launch (`ServerSetupPage`, `localStorage['9drive:server-url']` + `/api`; `getApiUrl()`/`getWebUrl()` in `lib/api.ts`), so the backend allows the Tauri origins in CORS (`DESKTOP_APP_ORIGINS`). Uploads and downloads run in Rust (`desktop/src-tauri/src`): `uploader/` keeps a queue in `uploads.json` in the app data folder, runs two files at a time, and sends bytes straight to Google (`direct: true` on `/uploads/resumable/init` returns the session URI; finishing calls `/uploads/resumable/status/:id`, which records the file through `finalizeResumableUpload`) or S3 (`/uploads/s3/:id/part-urls|parts|complete`; a bucket on a private network falls back to `POST /uploads`). `DELETE /uploads/resumable/:id` cancels either kind. The web side hands tokens to Rust (`uploader_configure`, re-sent on every `onAuthChange`); Rust refreshes on 401 and emits `auth://token`. `DesktopUploadProvider` mirrors the queue into the usual upload panel (bytes, smoothed speed, time left). S3 parts upload 4 at a time. Downloads (`download.rs`) probe with `Range: bytes=0-0`; when the server answers 206, files of 32 MB or more come down as 4 parallel ranges into a preallocated `<dest>.part`, with per-range progress in `<dest>.part.json`, so a retry or a later download to the same place resumes; otherwise (ZIPs, exported Google docs) one stream. Google sign-in and connecting accounts open the system browser with `client=desktop` (stored in `OauthState.client`); callbacks send the browser to the web app's `/desktop-return` page with a `ninedrive://google-auth|google-connected` link in the URL fragment (`utils/oauth-return.ts`); the page tells the user to go back and opens the link, which `DesktopBridge` handles once per link. A URL scheme must start with a letter, hence `ninedrive`. Releases: tag `desktop-v*` → `.github/workflows/desktop.yml` (draft release with updater `latest.json`, signed with `TAURI_SIGNING_PRIVATE_KEY`). Checks: `cd desktop/src-tauri && cargo clippy --all-targets && cargo test`, `cd frontend && npm run build:desktop`.

**Google sign-in and existing accounts.** `modules/auth/google-login.ts` is shared by both OAuth callbacks. If a Google sign-in matches a user whose email was never verified (`User.emailVerifiedAt` null, i.e. a password registration), that account's password, sessions, and API keys are reset so whoever registered the address first loses access.

**Backend module style.** The backend compiles to CommonJS (`module: NodeNext`, no `"type": "module"`), so relative imports need a `.js` suffix and `import.meta` is unavailable; use `__dirname`. Most route files hold their logic inline; services exist only for provider integrations (`google/`, `s3/`). Token encrypt/hash helpers are in `utils/crypto.ts`. Import Google APIs from `modules/google/google-apis.ts`, never `from 'googleapis'`: the package entry loads every Google API (`tsc` went to ~1.5 GB heap and failed self-update builds; runtime load is 120 MB vs 24 MB).

**Frontend API base URL.** `lib/api.ts` uses `VITE_API_URL` unless it's unset or still the default `http://localhost:4000`. In that case a production build falls back to `/api`, which `frontend/nginx.conf` proxies to `backend:4000` with request buffering off so streamed uploads work. Upload queue and progress state live in `context/UploadContext.tsx`. The PWA service worker (`vite.config.ts`) has a `navigateFallbackDenylist` of backend path prefixes, so add any new top-level backend route there.
